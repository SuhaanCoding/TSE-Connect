# Private matching and relevance evaluation

`npm run benchmark:matching` compares the frozen pre-change TF-IDF baseline, passage BM25, passage cosine similarity and fusion variants. It selects fusion on development NDCG@10 only. `data/matching-benchmark.json` contains aggregate results and limitations. The benchmark uses 293 distinct existing people, 42 cases (28 development / 14 holdout), 423 grades and 1140 document vectors. Grade 2 or 3 counts as relevant for recall, MRR and top-five success. NDCG uses exponential gains and logarithmic rank discounting.

Private inputs live in ignored `.local-backups/matching/`: `corpus.json` is an array of professional profile fields; `judgments.json` has `cases: [{id, split, kind, query, resume?, grades: {[profileId]: 0|1|2|3}}]`. `kind` is intent, resume or lookup. Label evidence and roster IDs are deliberately excluded from public Git history. Retain the input snapshots and checksums to reproduce this run. This benchmark is agent-reviewed, not independently human-labeled; zero means unsupported by the stored evidence, not lack of expertise. New relevance tuning should use a new development set and a fresh held-out set.

The encoder is pinned MiniLM-L6-v2, quantized int8, 384 dimensions, mean pooling, L2 normalization. Browser and offline encoders share passage preparation and tokenizer-budget splitting. A profile contributes member text, career overview, About and separate work/project passages. Long histories are sampled across their length. The scorer averages the best passage per query facet; explicit goal contributes 70% when resume context is also present. The selected fusion is 80% semantic cosine + 20% normalized passage BM25. Exact manually entered names and company names receive lookup priority. This is a retrieval heuristic, not predicted career value or response likelihood.

`npm run prebuild` checks the pinned public model SHA256 files, downloads missing files from the exact revision, and copies the matching/PDF runtimes from the lockfile. Model weights and runtimes are generated build assets, not Git blobs. No model-provider request is made while matching. The browser's optional first download is about 55 MB; standard matching downloads no inference model. All model/runtime URLs are same-origin. Ordinary result updates run in a worker, avoiding a blocked page.

`npm run matching:refresh` builds derived alumni vectors into the existing Supabase project's private `matching-vectors` Storage bucket. It needs the existing service credential. Do not make that bucket public or grant browser access. The authenticated API first loads the current RLS-visible directory; only those IDs with the matching current source hash and model version may use cached passages. Edits cannot return stale cached text. Immutable per-content records make concurrent refreshes safe; the aggregate index is only a fast manifest. Member bio/keyword changes and completed scrape webhooks schedule refreshes after their responses; missing vectors trigger a bounded lazy repair. Missing or failed vectors retain private word matching. Refresh the index after changing the model or passage format. Use a new model ID/path if replacing the public model weights, so browser model caches cannot mix revisions.

Resume PDFs/TXT are read in memory (5 MB, 10 pages, 30,000 characters). Password-protected, scanned, corrupt or oversized files get a paste-text alternative. Links, contact lines, email addresses and phone numbers are removed before matching. Raw file/text and goals never enter API requests, URLs, logs, persistent browser storage or member profile writes. Remove resume terminates the matching worker and clears this tab's draft/context; navigation/unmount also disposes the worker. Model caches contain public weights only. Existing shortlist IDs and manually edited outreach drafts retain their separate established storage rules.

Vercel installs ONNX Runtime in CPU-only mode (`ONNXRUNTIME_NODE_INSTALL=skip`). The two Linux CPU runtime files are explicitly traced; unused CUDA/TensorRT provider libraries are excluded even if a build cache contains them. This keeps functions within the existing 250 MB deployment limit without enabling larger functions.
