# Private matching and relevance evaluation

`npm run benchmark:matching` compares the frozen pre-change TF-IDF baseline, passage BM25, passage cosine similarity and fusion variants. It selects fusion on development NDCG@10 only. `data/matching-benchmark.json` contains aggregate results and limitations. The benchmark uses 293 distinct existing people, 42 cases (28 development / 14 holdout), 423 grades and 1140 document vectors. Grade 2 or 3 counts as relevant for recall, MRR and top-five success. NDCG uses exponential gains and logarithmic rank discounting.

Private inputs live in ignored `.local-backups/matching/`: `corpus.json` is an array of professional profile fields; `judgments.json` has `cases: [{id, split, kind, query, resume?, grades: {[profileId]: 0|1|2|3}}]`. `kind` is intent, resume or lookup. Label evidence and roster IDs are deliberately excluded from public Git history. Retain the input snapshots and checksums to reproduce this run. This benchmark is agent-reviewed, not independently human-labeled; zero means unsupported by the stored evidence, not lack of expertise. New relevance tuning should use a new development set and a fresh held-out set.

The encoder is pinned MiniLM-L6-v2, quantized int8, 384 dimensions, mean pooling, L2 normalization. Server and offline encoders share passage preparation and tokenizer-budget splitting. A profile contributes member text, career overview, About and separate work/project passages. Long histories are sampled across their length. The scorer averages the best passage per query facet; explicit goal contributes 70% when resume context is also present. The selected fusion is 80% semantic cosine + 20% normalized passage BM25. Exact manually entered names and company names receive lookup priority. This is a retrieval heuristic, not predicted career value or response likelihood.

`npm run prebuild` checks pinned model SHA256 files and downloads missing files from the exact revision for deployment. The same quantized model runs inside the existing Node.js Vercel function. There is no external model-provider call, browser model download or browser inference runtime. A warm instance reuses its encoder; cold starts load the bundled weights. Browser parsing still downloads the small PDF parser only when a PDF is selected.

`npm run matching:refresh` builds derived alumni vectors into the existing Supabase project's private `matching-vectors` Storage bucket. It needs the existing service credential. Do not make that bucket public or grant browser access. The authenticated API first loads the current RLS-visible directory; only those IDs with the matching current source hash and model version may use cached passages. Edits cannot return stale cached text. Immutable per-content records make concurrent refreshes safe; the aggregate index is only a fast manifest. Member bio/keyword changes and completed scrape webhooks schedule refreshes after their responses; missing vectors trigger a bounded lazy repair. Missing or failed vectors retain private word matching. Refresh the index after changing the model or passage format. Use a new model ID/path if replacing the public model weights, so browser model caches cannot mix revisions.

Resume PDFs/TXT are read in tab memory (5 MB, 10 pages, 30,000 characters). Password-protected, scanned, corrupt or oversized files get a paste-text alternative. Contact information is removed from extracted text. Matching uses authenticated same-origin POST /api/alumni/matches, with cleaned text, goal and lookup in the body. No raw file is uploaded. Private inputs and query embeddings are request-local on the server, absent from logs, profile writes and shared caches. They never enter URLs or persistent browser storage. Replies contain only sanitized profiles and bounded stored professional evidence; alumni/query vectors and full passage text stay on the server. Remove resume, switching to standard matching and unmount clear the client result cache and abort outstanding work. Draft editor text is retained only in the tab until explicit removal or navigation.

The server validates member access and current directory visibility on each new context. Per-instance admission bounds inference; it is not a distributed rate limiter. An unavailable model/cache visibly uses word matching. The client reuses at most two result sets in memory for filter, pagination and shuffle changes, avoiding repeated inference for the same experience/goal/search. No benchmark settings or model weights changed during the server migration.

Vercel installs ONNX Runtime in CPU-only mode (`ONNXRUNTIME_NODE_INSTALL=skip`). The ONNX JavaScript loader, shared runtime package and two Linux CPU runtime files are explicitly traced (Transformers uses createRequire, which automatic tracing misses); unused CUDA/TensorRT provider libraries are excluded even if a build cache contains them. This keeps functions within the existing 250 MB deployment limit without enabling larger functions. The postbuild bundle check fails if the model, loaders or CPU binaries are missing, or unused GPU providers enter the function.

The previous semantic GET format=paged-v1 protocol remains for already-open older clients. The current UI only sends the standard GET or matching POST; it does not download the passage/vector index. matching.worker.ts is retained solely as legacy source and is not imported by the current client.
